- **WhatsApp inbound media download + storage — DONE + DEPLOYED 2026-07-30**: Robert asked how JAG reads the amount off a payment-slip photo a tenant sends over WhatsApp — the honest answer at the time was "it doesn't, and you can't even see the photo in the app." `prop_whatsapp_messages` had a `media_url` column that had existed unpopulated since the table was created — the inbound webhook logged every IMAGE/DOCUMENT/AUDIO message as an empty row with `body = null` and nothing else, so a tenant's photo landed nowhere retrievable. **Built the storage half of that gap** (OCR/auto-read of the amount is a separate, not-yet-built piece):
  - `lib/whatsapp.ts` gained `downloadMedia(mediaId)` — Meta's inbound payload only carries a media *id*; the actual bytes live behind a second, short-lived Bearer-gated URL that has to be resolved in a follow-up call, done synchronously at webhook-receipt time since that URL expires in minutes.
  - `whatsapp-webhook.ts`'s `processInboundMessage` now downloads media **before** opening the DB transaction (a slow network round-trip has no business holding a Postgres connection open) and uploads it to MinIO (`BUCKET_DOCUMENTS`, key `owners/{ownerId}/wa-inbound/{fromNumber}/{waMessageId}.{ext}`), writing the object key into `media_url`. A download/upload failure is non-fatal — the message still logs, just without an attachment, rather than losing the whole inbound message over a Meta/MinIO hiccup.
  - **Bonus fix, same code path:** image/document captions were previously discarded outright (`body` was `null` for every non-text type) — a tenant captioning a payment photo "paid Aug rent" never reached the `isPaymentKw` classification branch and the caption never appeared anywhere. Captions now flow into `body` the same as a text message would.
  - `GET /properties/wa-inbox/media/:id` streams the object back, same auth-gated-streaming pattern as tenant documents (`docs/rules/storage-minio.md`) — added *above* the pre-existing `/:phone` route per the flat-route convention, though the two don't actually collide (different segment counts).
  - Frontend: both `TenantDetail.tsx` (per-tenant Messages tab) and `PropertiesWhatsAppPanel.tsx` (the main WA inbox both link to) render an `AuthedImg` thumbnail for `IMAGE` messages and an "Open attachment" link for `DOCUMENT`/`AUDIO`, both fetching via `api.objectUrl()` since a bare `<img src>` can't carry the Bearer token. 2 new i18n keys (`tenants.messages.attachment`, `tenancy.openAttachment`), English only per the translate-after-build convention.
  - No migration — `media_url` already existed in the schema, just unpopulated.
  - **A synthetic regression-test webhook POST accidentally used Ashante Charles's real phone number as the sender** while verifying the deploy didn't break normal text-message handling — the webhook's real auto-reply logic fired on it and sent her an actual (harmless but unexplained) WhatsApp message: "Got it — we'll get back to you shortly." Flagged to Robert immediately; noted in memory (`feedback_webhook_testing_real_phone`) so future webhook tests use an obviously-fake number.

No errors anywhere because the SQL was valid, just scoped to an owner with zero data. **Fix:** deactivated `testuser@jag.test` (`is_active = false`) and restarted `jag-api` to clear the 5-minute `ownerContextCache`.   - **"+ Add Tenant" never linked back to a matching application.** `POST /applications/:id/create-tenant` creates a tenant *and* backfills `prop_applications.tenant_id` — but `POST /properties/tenants` (`tenants-mortgage.ts`, the "+ Add Tenant" button) is a second, independent path into `prop_property_tenants` that never looked at `prop_applications` at all. We'll send full payment details closer to the date."` — 2 placeholders, no amount — but the code was sending a 3rd `currency` parameter with no matching `{{3}}` anywhere in the template. So this send had never once succeeded, for any tenant, independent of who owned the query. **Fix:** dropped the 3rd parameter to match the approved template exactly. Checked the other 5 rent-related templates (`jag_rent_reminder_d1`, `jag_rent_missed_d1`, `jag_rent_formal_demand`, `jag_rent_legal_notice`, `jag_rent_partial_payment`, `jag_rent_receipt_full_v2`) against their live Meta definitions via the Graph API — all match the code's parameter counts, no other landmines.
