"🚀 Start This Workout" just calls the existing `POST /sessions` with that `program_workout_id`.
- The prompt explicitly moderates intensity for elevated resting HR / high soreness / low sleep even when stated energy is high (verified live: AI correctly downgraded a "max energy" session to lower-volume/higher-rest after seeing a logged 78bpm resting HR) — and similarly for elevated cholesterol/triglycerides/glucose (shift toward cardio volume over max-strength), framed explicitly as general fitness-programming judgment, not diagnosis or medical advice.

**Bugs hit and fixed live, same session:**
- React StrictMode double-invokes `useEffect` in dev — `keycloak.init()` isn't idempotent (throws "can only be initialized once" on the 2nd call), which silently left local `npm run dev` sessions running fully unauthenticated (no redirect, no error surfaced) because `AuthProvider`'s `.catch()` still set `ready=true`. This is why local frontend dev against prod (the `jag-web` Vite proxy already pointed `/api` at `api.jagcorporate.com` before this session, but nobody had actually exercised the flow) had probably never really been tested. Fixed with a `useRef` guard in `AuthProvider.tsx`. Production is unaffected (StrictMode only double-invokes in dev).
- `SELECT DISTINCT` + `ORDER BY` where the select list had `session_date::text` but the ORDER BY used bare `session_date` — Postgres requires exact expression match under `DISTINCT`, threw `for SELECT DISTINCT, ORDER BY expressions must appear in select list`. Since the result was already being deduped in JS via `Set()`, removed the redundant `DISTINCT` rather than fixing the cast mismatch.

### Medical Records module (session 49, 2026-07-26)
Renamed Lifestyle's "Health Tracker" tab to **🩺 Medical Records** with three sub-tabs — **Profile** (default landing), **Records**, **Biometrics** (the old tracker, unchanged, still what the AI Fitness Coach reads). Built in response to Robert's session-48 stated direction: point Claude at a local folder of medical documents and extract structured data, without uploading the source documents themselves anywhere.

**Architecture decision — no local-model pipeline, no document upload:**
- Robert was explicit: source documents (a Dropbox folder, `C:\Users\rober\Dropbox\Family\PJA\Medical` for the pilot) **stay on the hard drive**, never uploaded to MinIO/the VM — only extracted structured data goes to JAG. `fam_medical_records.source_file_name` is a plain filename/path string for traceability, not an object key. Exception (not yet built): true identity documents (passport, license) still go through the existing DocVault path, unrelated to this module.
- Tested local-model extraction quality first (LM Studio running `google/gemma-4-e4b`, Ollama running `llava`/`llama3.2-vision`) against a real handwritten clinic card — both would likely mangle it. Given this is a one-time backlog import (~50 documents), not a recurring nightly job like the finance bank-statement pipeline, the call was: **Claude reads each source PDF directly (same vision capability as this chat) and writes the extraction**, no local-LLM script built for this. A future recurring-intake pipeline (new documents arriving over time) would be a smaller, separate follow-on if wanted.
- Every extracted record lands at `status='REVIEW'` — approval (or rejection) is a manual step in the UI; nothing is trusted automatically given medical-data stakes and how illegible some of the source scans were.

**Two-layer data model, not just a document log:**
- `fam_medical_records` (migration 029, jag_family, owner RLS) — the atomic per-document audit log. `record_type` enum (`LAB_RESULT`, `IMAGING`, `PRESCRIPTION`, `CLINIC_CARD`, `REFERRAL`, `DISCHARGE_SUMMARY`, `VISIT_NOTE`, `IMMUNIZATION`, `DEVICE_EQUIPMENT`, `INVOICE`, `CHRONOLOGY_SUMMARY`, `OTHER`), `specialty` (free text, matches the source folder structure — Back/Eye/Heart/Rheumatology/Urology/etc.), `details JSONB` (type-specific structured fields), `status` (`REVIEW`/`APPROVED`/`REJECTED`). `details.lifestyle_metrics` (optional array of `{metric_type, value, unit, entry_date}`) — on **approve**, any entries here are auto-inserted into `fam_lifestyle_tracker` too, so numeric lab values (cholesterol, glucose, resting HR) flow into the AI Coach's existing health-context query with zero coach changes needed.
- `fam_medical_profile` (migration 030, jag_family, owner RLS, one row per family member) — a **synthesized summary**: `active_diagnoses`/`current_medications`/`allergies`/`care_team` (JSONB arrays) + a narrative `summary_notes`. Added mid-session after Robert flagged that the Records tab alone read as "a bunch of scattered notes" with no synthesis — this is the actual answer to "what's going on with this person," built by Claude reading across the approved records, **not auto-computed by SQL** (the underlying records are too heterogeneous for a reliable mechanical rollup). `last_synthesized_at` makes staleness visible rather than silently assumed-fresh; re-synthesizing after new records are approved is a manual step (ask Claude), not automatic.
- Backend: `routes/lifestyle/medical-records.ts`, mounted at `/lifestyle/medical-records`. CRUD + `/approve` + `/reject` on individual records; `GET`/`PUT /profile/:familyMemberId` for the synthesized summary (PUT is a full-replace upsert).
- Frontend: `pages/Lifestyle.tsx` — `ProfileTab`/`ProfileView` (diagnoses/medications/care-team/allergies cards + narrative), `MedicalRecordsTab`/`MedicalRecordDetail` (list + approve/reject/delete), both added to the existing file; `TrackerTab` (biometrics) untouched. `api/medical-records.ts` new client module.

**Practical extraction notes for future sessions/other family members:**
- The `Read` tool's PDF support has a **20MB size cap** and its `pages` parameter frequently errors with "pdftoppm is not installed" on this machine for oversized files — full (no-`pages`) reads work up to that cap. For anything bigger: `pip install pypdf`, then split with `PdfReader`/`PdfWriter` (one page per file) and `Read` each split file individually. If the source PDF has extractable text (check with `page.extract_text()` first — some scans already have an OCR text layer baked in), pulling all pages as plain text in one pass is far cheaper than reading each page as an image.
- **CRITICAL, caught by Robert session 49:** text extraction is not safe to treat as complete on its own — any page that returns blank/garbled text (no OCR layer on that specific page, even in an otherwise-text-having file) got silently skipped in the first pass on the 71-page Medical Chronology file. **Always split every page and visually review any page with blank/garbled extracted text** — don't assume no-text means no-content. A second, distinct gotcha found on the same file: pages with clean extracted text can still get read but never written to the database — the fix there is a final page-by-page reconciliation, not better OCR. Full two-pass re-review (2026-07-27) covered every page of both the Chronology and X-Rays files and found/corrected both failure modes; see [[feedback-pdf-extraction-at-scale]] in memory.
- Not every document is a result: several files in this folder were **order/request forms** (blood test requests, imaging requests) with no actual values — logged as `OTHER` with an explicit "order form only, no results" note rather than misclassified as `LAB_RESULT`.
- Watch for duplicate/near-duplicate scans of the same physical card (this folder had the same immunization card and clinic card scanned twice under different filenames) — consolidate into one record rather than double-logging.
- Do not attempt to clinically interpret raw imaging films (X-rays/scans) yourself when there's no accompanying written radiology report — catalog them (dates, body region, patient ID) and say so explicitly rather than guessing at findings a radiologist would need to read.

### Samsung Health → Biometrics auto-sync via Android Health Connect (2026-07-27)
Robert asked for his S24 Ultra to automatically populate steps / active time / distance / sleep into his Biometrics. **Samsung has no cloud API for this** — the only path on Android is **Health Connect**, an on-device data broker. Health Connect collects nothing itself; Samsung Health is the app that actually runs the sensor algorithms and *writes into* it, so "read from Android" and "go through Samsung" are the same step. Because it's on-device only, the reader has to be **`jag-mobile`** — no server-side polling is possible.

- **Data flow:** Samsung Health → (on-device) Health Connect → `jag-mobile` reads on app open → `POST /lifestyle/tracker/health-connect-sync` → `fam_lifestyle_tracker` → Biometrics tab + AI Fitness Coach health-context query (which has no metric allowlist, so new metrics flow in automatically).
- **Migration 038 (jag_family):** adds `DISTANCE_KM` + `FLOORS_CLIMBED` (STEPS/SLEEP_HOURS/CALORIES/EXERCISE_MINUTES already existed) **plus a partial unique index** `(family_member_id, entry_date, metric_type) WHERE source = 'HEALTH_CONNECT'`. The partial-ness matters: the sync upserts one row per day per metric (re-opening the app mid-day updates the running total instead of duplicating), while manual entries keep their existing freedom to log several readings a day (e.g. BP morning + evening).
- **Endpoint** `routes/lifestyle/index.ts` — always writes to the owner's `relationship='SELF'` family member (this is Robert's own phone; never accepts a target member from the client). Returns 409 `SELF_MEMBER_NOT_FOUND` if no SELF row exists.
- **Mobile:** `src/services/healthConnect.ts` (+ `src/api/health.ts`), fired from `_layout.tsx` on cold start once `authed`. Syncs **today + previous 6 days** (`BACKFILL_DAYS = 7`) so a week without opening the app still self-heals. Sleep is queried with a **12h-wider window** than the calendar day, because a session that starts 11pm and ends 7am is timestamped by its end. `HealthSyncSchema`'s server-side entry cap was raised 50→200 alongside the widening — 7 days × 6 metric types (42) left almost no headroom, and a silent 422 on the whole batch as soon as a metric type is added (e.g. heart rate/SpO2 if a Galaxy Watch is ever paired) would have looked exactly like "sync stopped working" with no error surfaced anywhere.
- **Multi-source guard:** if more than one app writes the same metric (Robert has Google Fit installed, though not currently connected to Health Connect), summing every record **double-counts** — each app reports its own full tally of the same steps, not a partial share. `pickSingleSource()` prefers Samsung Health's `dataOrigin` (`com.sec.android.app.shealth`) and otherwise falls back to a single most-prolific origin, never a sum across origins.

**Four separate gotchas hit while getting this live — all silent failures, none produced a useful error:**
1. **`HealthConnectPermissionDelegate.setPermissionDelegate(this)` must be called in `MainActivity.onCreate`** (Kotlin, native). Without it the library's JS-side `requestPermission()` throws `UninitializedPropertyAccessException: lateinit property requestPermission has not been initialized` and **hard-crashes the app** on launch. Not optional; it's in the library's README but easy to miss when adding the dep from JS.
2. **Android 14+ requires a `ViewPermissionUsageActivity` activity-alias** (`android.intent.action.VIEW_PERMISSION_USAGE` + `android.intent.category.HEALTH_PERMISSIONS`, guarded by `android:permission="android.permission.START_VIEW_PERMISSION_USAGE"`). **This was the root cause of the longest dead-end.** Without it on Android 14+ (this device is Android 16 / SDK 36), Health Connect *launches* its `PermissionsActivity` and then **finishes it ~100ms later without ever rendering**, and the request returns "denied" — no crash, no error, nothing on screen, and the app never appears under Health Connect's "Your health apps" list. The older `androidx.health.ACTION_SHOW_PERMISSIONS_RATIONALE` intent-filter only covers Android 13 and below and is **not** a substitute. Diagnosing it required watching `PermissionsActivity` open+close in raw logcat.
3. **Android allows only one permission dialog in flight at a time.** The notifee notification-permission request fires on cold start too and would win the race, starving the Health Connect request (logged only as `W Activity: Can request only one set of permissions at a time` — no crash, no dialog). Health Connect sync is therefore deliberately delayed ~4s after `authed`.
4. **`minSdkVersion` had to go 24 → 26** for the Health Connect library.

**Pre-existing bug found and fixed along the way (unrelated to Health Connect):** the app had **two independent biometric gates** — `_layout.tsx`'s app-level lock screen *and* a second auto-prompting one in `login.tsx`. This caused repeated fingerprint prompts, and `login.tsx` navigating before `_layout.tsx`'s `<Stack>` had mounted threw *"Attempted to navigate before mounting the Root Layout component"* — which `login.tsx` caught and displayed as a misleading **"Biometric error"** alert (the fingerprint auth itself always succeeded). Fixed by removing `login.tsx`'s duplicate biometric flow entirely and gating both files' navigation on **`useRootNavigationState()?.key`** — expo-router's real readiness signal. **A fixed `setTimeout` is not a valid fix here** (tried, and it crashed *harder* — uncaught, outside the try/catch): navigator attach time varies with native bridge round trips, so wait on the actual signal.

**Verified live, confirmed twice:** first pass landed 3 days of real data (steps/distance/calories); after widening to a 7-day backfill and a second confirmed sync, 22 rows spanning Jul 21–27 are in `fam_lifestyle_tracker` attributed to Robert's SELF record — including one `EXERCISE_MINUTES` entry (46 min, Jul 21) that only surfaced once the window widened past 3 days. **Sleep and floors have still returned nothing** — not a bug: phone-only tracking with no Galaxy Watch, and Samsung Health had no sleep sessions or floor data logged for these days. Those metric types are already wired end-to-end and will populate automatically if/when Samsung Health records them (a Galaxy Watch would add heart rate, SpO2 and sleep staging, which would need new metric types).

**Do NOT log the sync payload** — `console.log` of health entries goes to logcat, readable by anything with adb access. Diagnostic logging was used during the build-out and deliberately stripped before shipping.
