Nightly `backup-databases.sh` (VM cron, 02:00 UTC) had been running every night since creation (~2026-06-12) but **never once completed successfully** — found and fixed 2026-07-21/22.

**Two stacked bugs, both silent:**
1. `/var/log/jag-backup.log` was never pre-created + chowned to `ubuntu` (every other cron script's log had this done; this one was missed). `/var/log` is root:root 755, so `ubuntu`'s cron redirect (`>> /var/log/jag-backup.log`) couldn't create the file — the whole run failed before logging anything, with zero trace in cron's own logs.
2. The script's `mc alias jag` (used for the MinIO upload step) still held the **pre-rotation MinIO root password** — never updated after the 2026-06-24 credential rotation (see [[feedback-compose-env-precedence]] and secrets rotation history). Even if bug 1 were fixed, uploads would 403.

**Confirmed via the evidence, not assumption:** `jag-backups` MinIO bucket was 0 bytes since creation (2026-06-12) until this fix — proof zero backups had ever landed there, despite `journalctl` showing cron firing nightly for weeks.

**Fix applied:** `sudo touch` + `chown ubuntu:ubuntu` the log file; `mc alias set jag ...` refreshed with current `MINIO_ROOT_PASSWORD` from `/opt/jag/jag-infra/.env`; also found+fixed a secondary issue — the retention-prune step choked every run on `/opt/jag/backups/pre-rotation-20260624_201000` (owned by `postgres`, not `ubuntu`, from a manual rotation-safety snapshot) — chowned to `ubuntu` (not deleted, still serves as rollback material). Verified end-to-end: exit code 0, all 5 DBs dumped + uploaded + pruned correctly on a clean re-run.

**Local off-instance pull added (2026-07-21):** `scripts/db-backup-pull/pull-backups.ps1` (tracked in repo) — SSHes into the VM, lists actual date-named dirs under `/opt/jag/backups/` (queries reality rather than guessing date strings — VM runs UTC, workstation runs local TT, a naive `Get-Date` match missed the VM's folder on the first attempt), pulls the 3 most recent date dirs' `.dump` files down to `C:\Users\rober\JAG-DB-Backups\` (outside the git repo, not tracked), prunes local copies older than 90 days. Registered as Windows Scheduled Task **`JAG-DB-Backup-Pull`**, daily at **7:00 AM** local (safely ~9h after the VM's 02:00 UTC / 22:00 TT backup completes). Verified working end-to-end (manual run pulled real dump files). This is now the actual off-instance copy — the MinIO `jag-backups` bucket lives on the same Oracle instance as the data it protects, so it alone doesn't survive a full instance loss.

**Coverage extended to Traccar + Documenso (2026-07-21, same session):** `backup-databases.sh`'s `DATABASES` array extended from 5 to 7 (`+ traccar + documenso`), plus reconciled a drift — the deployed VM copy had a `PG_HOST`/`PG_PORT` fix (Unix socket peer auth) that had never been synced back to the git-tracked copy in `jag-infra/scripts/`; both are now in sync. Verified end-to-end: all 7 DBs dump + upload + the local pull script picks them up automatically (no changes needed there — it just mirrors whatever's in the VM's dated folder). `postgres` superuser had no permission issues dumping `traccar`/`documenso` despite being owned by `traccar_app`/`documenso_app` roles.

**Keycloak added too (same session, 2026-07-21):** `DATABASES` array extended to 8 total (`+ keycloak`). Verified clean run (`databases_dumped:8, databases_total:8, exit_code:0`), local pull confirmed. All auth/user-account/WebAuthn data now covered.

- **`docuseal` database still exists on the VM** (dead — DocuSeal was fully superseded by Documenso per [[project-esignature-documenso]]) — left out of backup coverage deliberately, orphaned data not worth preserving.

**MinIO file buckets added too (2026-07-21/22, same session):** the 5 tenant-facing file buckets (`jag-photos`, `jag-documents`, `jag-receipts`, `jag-bank-statements`, `jag-signed-documents` — actual files, not just DB rows referencing them) were completely uncovered by anything above. Total footprint is tiny (~62-63MB, 78 objects as of 2026-07-22 — `mc du` confirmed per-bucket). Added:
- New script `jag-infra/scripts/backup-minio-buckets.sh` (repo-tracked + deployed to `/opt/jag/jag-infra/scripts/` on the VM) — `mc mirror --remove` (point-in-time snapshot, not an ever-growing archive) each bucket into `/opt/jag/backups/<date>/minio-buckets/<bucket>/`, same dated-folder convention `backup-databases.sh` uses. Reuses the same `jag` mc alias — no new credentials. Structured JSON logging (`entity: MINIO_BACKUP`), same style as the DB script.
- Pruning is by **directory-name date, not mtime** — mtime on the parent date-dir gets bumped by the mirror write itself (would falsely look "fresh" forever), and a naive mtime-based prune risked touching the sibling `*.dump` files that the DB script's own pruning owns. Parses `YYYY-MM-DD` from the dir name instead.
- Cron installed at **02:15 UTC** (15 min after the 02:00 DB dump, avoids I/O contention): `/var/log/jag-minio-backup.log` pre-created + chowned to `ubuntu` up front this time (the DB script's very first bug, log-file-didn't-exist-so-cron-redirect-silently-failed, was pre-empted here from the start).
- Verified clean run: `buckets_total:5, exit_code:0`, all 5 mirrored (jag-photos 30 files/11M, jag-documents 40/50M, jag-receipts 0/empty, jag-bank-statements 4/1.3M, jag-signed-documents 4/1.3M).
- **`pull-backups.ps1` extended** to also grab the `minio-buckets/` subdir — tars it on the remote side first (same "don't `scp -r` a directory full of small files" lesson as the `prod_modules`/`dist` deploy issue, even though this dataset is small enough it'd probably survive `scp -r` — did it properly anyway for consistency), then extracts locally. **Hit a *different*, Windows-specific tar bug while wiring this up:** the git-bash `tar` that's first on PATH in this environment misparses any argument containing a Windows drive letter (`C:\Users\...`) as a remote `host:path` tape spec (`Cannot connect to C: resolve failed` / silently truncates the path even with `--force-local` on `-C`). Fixed by `Push-Location` into the target dir and extracting with a bare relative filename — colons never appear in any tar argument. Verified end-to-end: all 78 files landed locally with byte-for-byte matching sizes vs. the VM's `mc du` output.

**Secrets + Keycloak realm config added too (2026-07-22, same session) — this closes out the last open gap:**
- New script `jag-infra/scripts/backup-secrets.sh` (repo-tracked + deployed) — bundles `/opt/jag/jag-infra/.env` (authoritative compose interpolation file), `/opt/jag/.env` (older, still-referenced-by-some-scripts file — see [[project-secrets-and-env]]), `/opt/jag/jag-infra/.cron-secrets`, and `/opt/jag/jag-api/google-calendar-key.json` into `/opt/jag/backups/<date>/secrets.tar.gz`, permissions `0600`. Also runs a Keycloak **partial-export** (`kcadm.sh create realms/jag/partial-export?exportClients=true&exportGroupsAndRoles=true`) — captures clients/roles/flows/WebAuthn policy/mappers, deliberately NOT user accounts/credentials (those are already covered by the `keycloak` DB dump in `backup-databases.sh`).
  - `kcadm.sh` on this Keycloak 26 image doesn't support `--no-config` (errors "Unsupported option") — must always pass `--config <path>` explicitly to both the `config credentials` step and the `create` step, using a per-run temp file under `/tmp` inside the container, deleted after.
  - Deliberately **not** uploaded to the MinIO `jag-backups` bucket like the DB dumps are — secrets shouldn't live in the same storage system they unlock.
  - Cron installed at **02:30 UTC** (15 min after the MinIO mirror). Log file pre-created + chowned to `ubuntu` from the start (same lesson as the other two scripts, applied proactively this time).
  - Verified clean run: 4/4 env files copied + Keycloak export succeeded, bundled to a 20K `0600` tar.
- **`pull-backups.ps1` extended a third time** to plain-`scp` `secrets.tar.gz` down (single small file, no tar-of-tar dance needed unlike the MinIO buckets step). Left as a **compressed, unextracted tar** in the pull directory deliberately — it holds every live credential the platform runs on, so it shouldn't sit around as loose plaintext `.env` files on the local disk. Extract only when actually needed for a restore. Verified: tar landed locally, `tar -tzf` listing confirmed all 5 expected entries (`keycloak-realm-export.json`, `google-calendar-key.json`, `opt-jag.env`, `jag-infra.env`, `cron-secrets.env`) without extracting.

**All identified backup gaps are now closed.** VM-side, three cron jobs run nightly in sequence (02:00 DB dumps → 02:15 MinIO bucket mirrors → 02:30 secrets + Keycloak realm export), all writing into the same `/opt/jag/backups/<date>/` folder. One local pull script (`JAG-DB-Backup-Pull` scheduled task, 7 AM daily) mirrors that whole folder off-instance to `C:\Users\rober\JAG-DB-Backups\<date>\`. Local project directory (source) is separately covered off-site via `deploy.sh` Step 8 auto-commit + push to private GitHub repo `robertjohnsonattin-cmd/jag-platform`.

Pattern worth remembering (added here too, applies to all 3 scripts): **pre-create and `chown ubuntu:ubuntu` any new cron log file before the cron entry ever fires** — this was the root cause of the original DB-backup silent failure, and was correctly done proactively for both the MinIO and secrets scripts this session instead of being discovered the hard way again.

**Manual restore test run across all 8 DBs (2026-07-22, same session):** before automating it, ran a real restore test by hand — pulled each dump from the *local off-instance copy* (not the VM's own file, to validate the whole chain including the round trip), uploaded back to VM `/tmp`, MD5-verified intact, `pg_restore`'d into a throwaway `<db>_restore_test` database, compared table counts + spot-checked a representative row against live, then cleaned up. All 8 passed (jag_core, jag_commercial, jag_entertainment, jag_family, jag_properties, traccar, documenso, keycloak) — table counts matched exactly, spot-check rows matched exactly.

**Weekly automated restore test added (2026-07-22, same session):** `jag-infra/scripts/restore-test.sh` — runs Sunday 03:00 UTC (1h after the secrets backup), restores that night's dump for all 8 DBs into `<db>_restore_test`, verifies, cleans up. Verification logic went through one important correction:
- **First version compared exact row counts against LIVE data and failed 5 of 8 DBs on real production data** — not a real bug, a flaw in the test design. Comparing a dump taken at 02:00-02:30 UTC against live data queried hours later will always show small drift on busy tables (Traccar GPS pings, Keycloak sessions, Documenso webhook events) — that's normal write activity, not corruption.
- **Fixed:** success now requires (1) `pg_restore` exit 0, (2) **exact** table-count match (schema-level — this only changes on a real migration, so it's a reliable signal), and (3) row-count gap under 5% (tolerates natural churn during the test window, still catches real data loss like a truncated dump). Re-ran against the same live data — all 8 passed cleanly.
- Row-count comparison uses a generic `query_to_xml`/`xpath` trick to sum `SELECT count(*)` across every table dynamically — no hardcoded table names to go stale as schemas evolve.

**Cron logs had zero Loki/Grafana coverage — fixed alongside this (2026-07-22):** discovered while wiring this up that promtail's scrape config only ever covered Docker container logs + a (dead/misconfigured) native-PostgreSQL log path — **none** of the `/var/log/jag-*.log` files that `backup-databases.sh`/`backup-minio-buckets.sh`/`backup-secrets.sh`/`restore-test.sh` write to were ever scraped. A failure in any of these 4 scripts would sit in a file nobody was watching — the *exact* blind spot that caused the original month-long silent DB-backup failure this whole effort started from. Fixed: added a `/var/log:/var/log/host:ro` mount to the `promtail` service + a new `jag-cron-scripts` scrape job parsing the scripts' JSON (`entity`/`action`/`severity` promoted to Loki labels). Verified end-to-end via a direct Loki API query (`{job="jag-cron-scripts",entity="RESTORE_TEST"}` returned real log lines with labels correctly parsed). **Gotcha hit during verification:** a manual `bash script.sh` run (no `>>` redirect) doesn't write to the log file at all — the log only fills when actually invoked the way cron does (`>> logfile 2>&1`); wasted one round of "why isn't this in Loki" debugging before catching that the file itself was still 0 bytes.

**Grafana alert wired to the JAG bell (2026-07-22, same session) — the loop is now fully closed, not just logged:** a failing backup/restore script now actually notifies Robert, not just sits in Loki waiting to be looked at.
- New internal route `POST /internal/grafana-alert-webhook` (jag-api, Bearer-token, Docker-network-only, same pattern as `/internal/minio-audit`/`/internal/traccar-event`) — receives Grafana's alert webhook payload, calls `enqueueNotification()` (tier 1, JAG bell), deduped 3h per alert rule name (identical dedup pattern to the existing GPS-battery-sync-failure alert in `traccar-event.ts`).
- Grafana alert rule provisioned via `jag-infra/grafana/provisioning/alerting/backup-alerts.yml.template` — LogQL `count_over_time({job="jag-cron-scripts", severity="ERROR", entity=~"BACKUP|MINIO_BACKUP|SECRETS_BACKUP|RESTORE_TEST"}[15m]) > 0`, 15m eval interval, `for: 0m` (fires immediately, no pending period).
- **Real bug caught during testing, not hypothetical:** an unscoped query (`job="jag-cron-scripts"` alone, no `entity` filter) would fire on **any** cron script's error, not just backup ones — the same `job` label covers every `jag-*.log` file (rent reminders, viewing reminders, GPS battery, etc.) per the earlier promtail wiring. Proved this concretely: a real pre-existing `auth_fail` ERROR in `jag-post-viewing.log` (unrelated to backups — **not yet triaged, worth a separate look**) matched the unscoped query during testing. Fixed by adding the `entity=~"BACKUP|MINIO_BACKUP|SECRETS_BACKUP|RESTORE_TEST"` filter.
- **Secret handling:** the webhook needs a bearer token in the Grafana contact-point config, but that can't be committed in plaintext (STD-07). Solution: track `backup-alerts.yml.template` (placeholder `__GRAFANA_ALERT_WEBHOOK_TOKEN__`) in git; `jag-infra/scripts/render-grafana-alerts.sh` substitutes the real token from `.env` into the actual `backup-alerts.yml` on the VM only (gitignored) — same convention as `.env.example` vs `.env`.
- Uses Grafana's **per-rule `notification_settings.receiver`** (Grafana ≥10.3 "simplified routing") rather than editing the global notification-policy tree — keeps this addition isolated so a future second alert doesn't have to worry about interacting with this one's routing.
- **Gotcha hit during setup:** first render used `chmod 600` on the rendered file — broke Grafana's provisioning with a silent-looking `permission denied` (Grafana's container reads the bind-mounted file as its own non-root UID, not the host `ubuntu` owner). Fixed to `644` (the containing directory itself is only reachable via the VM/Docker anyway, so this isn't a real exposure).
- **Verified end-to-end for real, not just configured:** tested the webhook directly first (401 unauthenticated, 200 + real `notification_queue` row authenticated, cleaned up). Then verified the *actual Grafana alerting engine* fired autonomously — wrote a synthetic `severity=ERROR` line to `jag-restore-test.log`, and Grafana's own scheduler picked it up, fired the rule, called the webhook, and created a real notification row on its own (not something I POSTed manually) — the strongest possible proof the whole chain works, not just its individual pieces.
- Committed `4c723bc`, pushed. `GRAFANA_ALERT_WEBHOOK_TOKEN` generated via `openssl rand -hex 24`, stored in VM `/opt/jag/jag-infra/.env` and wired into the `api` service's `environment:` block in `docker-compose.yml` (the recurring "value exists in `.env` but was never actually wired into the service" gap — checked and avoided this time).

**Follow-up investigated same session (2026-07-22):** the `auth_fail` ERROR found above was traced further — see [[project-cron-ropc-auth-failures]] for the full finding. Not a backup-pipeline issue; unrelated pre-existing bug surfaced only because the new alert-scoping test happened to go looking at the same log stream.

Pattern worth remembering: **a cron job showing up in `journalctl` as "executed" is not proof it did anything** — check for actual output/log growth, not just invocation. Also: **don't guess date strings across a VM (UTC) and local workstation (local tz) boundary** — query the remote for what actually exists rather than computing `Get-Date`/`date` locally and assuming it matches.
